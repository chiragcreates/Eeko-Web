__Eeko-Web PNG Card Format__

This document describes the binary envelope and image encoding used by Eeko-Web to carry encrypted messages in PNG image cards.

__1. Overview__

Eeko-Web stores encrypted message data inside a PNG image using a custom grid-based encoding scheme.

The PNG is a carrier for the binary data. It does not provide encryption itself.

The process has two stages:

1. Create an encrypted binary envelope.
2. Encode the envelope into a grid of image cells.

Decryption reverses these stages to recover the encrypted envelope and authenticate the original message.

__2. Binary Envelope__

The encrypted envelope uses the following layout:

| Field | Size | Description |
| :--- | :---: | :--- |
| Magic bytes | 4 bytes | Identifies the envelope as Eeko's supported format |
| Version | 1 byte | Identifies the envelope format version |
| Iteration count | 4 bytes | PBKDF2 iteration count, big-endian |
| Salt | 16 bytes | Random salt used for password-based key derivation |
| Nonce | 12 bytes | Random AES-GCM nonce |
| Ciphertext and authentication tag | Variable | Encrypted message data and its authentication tag |


The magic bytes are "SQCR".

The format version is currently "1".

New cards use a PBKDF2 iteration count of "600000". The decoder accepts iteration counts from "100000" through "2000000", subject to successful validation and decryption.

The ciphertext includes the authentication tag produced by the Web Crypto API.

__3. Payload Length Prefix__

Before the envelope is encoded into image cells, the binary payload is prefixed with a 4-byte unsigned big-endian length value.

This length specifies the number of envelope bytes that follow it.

The length prefix helps the decoder determine how many reconstructed bytes belong to the payload.

The decoder should reject invalid lengths and truncated payloads instead of attempting to decrypt incomplete data.

__4. Grid-Based Image Encoding__

Eeko-Web represents the length-prefixed payload as a sequence of bits.

Each bit is represented by one square cell in the PNG image.

| Parameter | Value |
| :--- | :--- |
| Cell size | 16 × 16 pixels |
| Image margin | 120 pixels |
| Orientation anchors | 3 |
| Anchor size | 60 × 60 pixels |
| Anchor inset | 20 pixels |


The grid dimensions are selected to accommodate the payload, with the number of rows and columns arranged approximately square.

Bit representation

- A bit value of "1" is represented by a black filled cell.
- A bit value of "0" is represented by a light-gray outlined cell.

The decoder samples pixel colors at cell centers to reconstruct the encoded bit sequence.

__5. Orientation Anchors__

Three black square anchors are rendered near the top-left, top-right, and bottom-left portions of the image.

Each anchor measures 60 × 60 pixels and is inset 20 pixels from its corresponding image edges.

These anchors provide visual reference points for the intended card layout. They are part of the image design, not part of the encrypted binary envelope.

The decoder relies on the expected image layout and grid geometry. Arbitrarily resized, cropped, compressed, or edited images may not decode correctly.

__6. Encoding Process__

The encoding process is:

1. Encrypt the plaintext using AES-GCM.
2. Construct the binary envelope.
3. Prefix the envelope with its 4-byte length.
4. Convert the length-prefixed payload into bits.
5. Determine a grid layout that can hold all bits.
6. Render the grid cells and orientation anchors.
7. Export the resulting image as PNG.

PNG is used because it supports lossless image storage, which helps preserve the cell patterns needed for decoding.

__7. Decoding Process__

The decoding process reverses the encoding steps:

1. Load the PNG image.
2. Read pixel data through the Canvas API.
3. Sample the expected grid-cell centers.
4. Reconstruct the bit sequence and convert it into bytes.
5. Read the 4-byte payload length.
6. Extract and validate the envelope.
7. Parse the format metadata, salt, nonce, and ciphertext.
8. Derive the encryption key and authenticate the ciphertext.
9. Return the plaintext only when decryption succeeds.

Malformed, incomplete, or unsupported data should be rejected safely.

__8. Compatibility__

Compatibility depends on the binary envelope, payload length convention, bit order, grid dimensions, anchor layout, and decoder behavior remaining consistent.

Changes to any of these details may prevent older cards from decoding correctly.

Future format changes should use an explicit versioning strategy and include regression tests with cards generated by previous supported versions.

Compatibility with Eeko's Python encoder or decoder must be verified through testing. A shared name or similar visual format does not guarantee binary compatibility.

__9. Limitations__

- The card layout is not intended to survive arbitrary resizing or cropping.
- The PNG pattern is not encryption; confidentiality comes from the encrypted envelope.
- A copied image can be shared with others.
- Successful decoding of the image does not guarantee that its encrypted contents can be authenticated or decrypted.
- The implementation should validate all lengths, offsets, and supported metadata before processing data.
